PA1 — Answer for 4.3 (File transfer timing) / T7

How I measured
--------------
I used the provided client in “file” mode and varied the buffer capacity (-m).
All runs launched the server as a child from the client. Commands:

  # small CSV
  ./client -f 10.csv
  ./client -f 10.csv -m 8192

  # large binary (sparse) file
  truncate -s 100M BIMDC/test.bin
  ./client -f test.bin -m 65536

The client prints the file size and elapsed time; I computed throughput as
(size in MiB) / (time in s). 1 MiB = 1,048,576 bytes.

Results
-------
File          Size (bytes)   -m (bytes)   Time (s)   Throughput (MiB/s)   Notes
------------  -------------  -----------  --------   --------------------  -------------------------------
10.csv        289,955        256          0.066      ~4.19                 many small chunks over FIFO
10.csv        289,955        8192         0.005      ~55.3                 larger chunks = fewer syscalls
test.bin      104,857,600    65,536       0.528      ~189.4                100 MiB, created via truncate

(Throughput calculations:
- 10.csv @0.066s: (289,955 / 1,048,576) / 0.066 ≈ 4.19 MiB/s
- 10.csv @0.005s: (289,955 / 1,048,576) / 0.005 ≈ 55.3 MiB/s
- 100 MiB @0.528s: (104,857,600 / 1,048,576) / 0.528 ≈ 189.4 MiB/s)

Observations
------------
• Increasing the buffer capacity (-m) dramatically improves throughput because it reduces the number of request/response cycles.  
• With -m=256, transferring even a small file requires many chunks → lots of read/write system calls, context switches, and user↔kernel memory copies.  
• With -m in the tens of KiB, the number of chunks drops by ~O(buffer_size), so syscall and context-switch overheads shrink and throughput rises.

Main bottleneck (qualitative)
-----------------------------
For large transfers over FIFOs, the primary bottleneck is IPC overhead: each chunk incurs at least one write by the client and a read by the server (plus the reverse for the reply path), which means:
  • multiple system calls per chunk,
  • context switches between processes,
  • user→kernel→user memory copies.

As -m grows, this fixed per-chunk cost is amortized over more bytes, so performance improves until it’s limited by memory copy bandwidth and the kernel’s pipe throughput. Disk I/O was not dominant in the 100 MiB test.bin case because the file was created with `truncate` (sparse file), so reading mostly returns zeros from the filesystem without real disk reads; this highlights the IPC/memcpy overhead as the main limiter here.

Reproduce / verify
------------------
• Compare files after transfer:
    diff BIMDC/10.csv received/10.csv
    diff BIMDC/test.bin received/test.bin
  (no output means identical)
• Try other sizes:
    truncate -s 10M  BIMDC/t10.bin && ./client -f t10.bin -m 65536
    truncate -s 200M BIMDC/t200.bin && ./client -f t200.bin -m 65536
  and extend the table similarly.

Conclusion
----------
The dominant cost for this FIFO-based design is per-chunk IPC overhead (syscalls, context switches, and memory copies). Using larger message sizes reduces these costs and increases throughput; at high -m values the transfer approaches limits set by kernel pipe bandwidth and memory copy speed. (If the source file required real disk reads, storage throughput could become the bottleneck instead.)
